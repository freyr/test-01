git push: wyślij commity na GitHub

{{sesja push}}

Najważniejsza linia to cbbd694..12f2637 main -> main. Gałąź main na GitHubie przesunęła się z commita cbbd694 (zadanie 3) na 12f2637 (zadanie 5). Teraz HEAD i origin/main wskazują ten sam commit, a git status pisze up to date.

Po minucie lub dwóch GitHub Pages publikuje nową wersję strony. Postęp widzisz na GitHubie w karcie Actions.

Przy pierwszym git push możesz zobaczyć prośbę o login i hasło. To znaczy, że repozytorium ma adres HTTPS. Sprawdź git remote -v i sklonuj repozytorium jeszcze raz adresem SSH.

Odrzucony push

Następnego dnia w szkole John robi zadanie 6. Zapomina, że wczoraj w domu wysłał commit z README.

{{sesja odrzucony 1-4}}

GitHub odrzucił push (rejected). Na GitHubie jest commit z README, którego nie ma na szkolnym komputerze. Git nie nadpisze cudzej pracy, nawet jeśli to Twoja praca z innego komputera. Podpowiedź hint: mówi, co zrobić: git pull, potem znowu git push.

{{sesja odrzucony 5-7}}

git pull pobrał commit z README i przełożył commit z zadaniem 6 na koniec historii (Successfully rebased). Tak działa ustawienie pull.rebase true z lekcji 4. Historia jest prosta: README, a po nim zadanie 6. Commit z zadaniem 6 dostał nowy hash, d0d7e0c zamiast 39f3882, bo ma teraz innego rodzica.

Zasada: zacznij pracę od git pull, zakończ pracę git push. Wtedy odrzucony push zdarza się rzadko.

Konflikt

Czasem w obu commitach zmieniła się ta sama linia tego samego pliku. Wtedy Git nie wie, którą wersję wybrać, i zgłasza konflikt (CONFLICT). W pliku zobaczysz znaczniki:

<<<<<<< ...
wersja z GitHuba
=======
Twoja wersja
>>>>>>> ...

Zostaw właściwą wersję, usuń znaczniki i zapisz plik. Potem wykonaj git add plik i git rebase --continue. Aby zrezygnować i wrócić do stanu przed git pull, wykonaj git rebase --abort. Gdy pracujesz sam i zaczynasz od git pull, konflikt prawie się nie zdarza.

Ćwiczenie

  1. Wyślij commity z zadań 4 i 5 przez git push.
  2. Na GitHubie sprawdź listę commitów i stronę na github.io.
  3. Na GitHubie zmień README.md przez stronę WWW (ikona ołówka) i zrób commit.
  4. Na komputerze zrób zadanie 6 i commit, bez git pull. Spróbuj git push. Przeczytaj błąd.
  5. Napraw sytuację przez git pull i git push. Sprawdź historię.

Sprawdź się

Co znaczy cbbd694..12f2637 main -> main?

Gałąź main na GitHubie przesunęła się z commita cbbd694 na 12f2637.

Push został odrzucony z napisem fetch first. Co robisz?

git pull, a potem znowu git push.

Dlaczego po rebase commit z zadaniem 6 ma inny hash?

Hash zależy także od rodzica commita. Po rebase rodzicem jest commit z README, więc hash jest nowy.

Jaka zasada chroni przed odrzuconym pushem?

Zaczynaj pracę od git pull, kończ git push.
